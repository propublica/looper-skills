# AGENTS.md

Instructions for coding agents working in this repo. See [`CONTRIBUTING.md`](CONTRIBUTING.md)
for the human-oriented version of the same workflows.

## What this repo is

A collection of [Agent Skills](https://www.anthropic.com/engineering/equipping-agents-for-the-real-world-with-agent-skills)
for spreadsheet inference, each hand-ported to a Gemini Gem. There's no application
code here — the artifacts are the skill's `SKILL.md` + supporting files, and the
Gem's `instructions.md` + knowledge files.

## Repo layout

```text
skills/<skill-name>/
  SKILL.md              # required — frontmatter name: must equal <skill-name>, kebab-case
  assets/                # files referenced by the skill at runtime
  references/            # background material the skill reads on demand
  evals/evals.json       # required — test scenarios, see below

gems/<skill-name>/
  README.md              # deploy steps + what's hand-edited vs. copied
  instructions.md         # Gem's system instructions, ported from SKILL.md
  knowledge/              # ported from skills/<skill-name>/assets|references
  diff-pairs.txt          # hand-edited: which skill file maps to which Gem file
  known-diffs.txt         # generated: `./gems/check-diffs.sh --record <skill-name>`
```

## Making a change

If your harness has a skill-authoring skill available (e.g. `skill-creator`, or
`superpowers:writing-skills`), use it for any change to a `SKILL.md`'s content —
not just formatting. That's the intended workflow for this repo (see
[Evaluating a skill](CONTRIBUTING.md#evaluating-a-skill)), and it knows the
iteration loop — draft, eval, revise — that a direct edit skips. If none is
available, at minimum follow the Agent Skills spec's guide:
<https://agentskills.io/skill-creation/evaluating-skills>.

**Editing an existing skill** (`skills/<name>/SKILL.md` or its assets/references):

1. Make the change.
2. If the corresponding Gem file is in that skill's `gems/<name>/diff-pairs.txt`,
   run `./gems/check-diffs.sh <name>` — it will fail with `DRIFT DETECTED` if the Gem
   wasn't updated to match. Port the change into the Gem's file, then re-run with
   `--record` to update `known-diffs.txt`. Note the change in the Gem's README too.
3. Update `evals/evals.json` if the change affects behavior the evals cover.
4. Record a real benchmark/eval run in the commit message — run results aren't
   committed as a file (see [Evaluating a skill](CONTRIBUTING.md#evaluating-a-skill)).

**Adding a new skill**: see [Proposing a new skill](CONTRIBUTING.md#proposing-a-new-skill).
It needs `SKILL.md`, `evals/evals.json`, and — if it should reach Gemini users —
a Gem under `gems/<name>/` with its own `diff-pairs.txt`. A gem directory with no
`diff-pairs.txt` fails CI, not silently skips.

## Validating before you're done

```bash
./build.sh <skill-name>      # fails if directory name and frontmatter name: disagree,
                              # or if the name isn't lowercase kebab-case
./gems/check-diffs.sh        # fails on any undocumented skill/gem drift
```

Both run in CI (`.github/workflows/release.yml` on tag push,
`.github/workflows/check-gem-diffs.yml` on any push/PR touching `skills/` or `gems/`).

## Things not to do

- Don't commit `.skill` files or anything under `dist/` — `.gitignore` excludes them;
  they're built by CI from tagged source.
- Don't rename a skill directory without updating the `name:` frontmatter in its
  `SKILL.md` to match — `build.sh` treats a mismatch as a hard error.
- Don't hand-edit a Gem's `known-diffs.txt` — it's generated by
  `./gems/check-diffs.sh --record`, not written by hand.
- Don't add fallback/compat code for old skill formats — there's no versioning
  concern here, just edit the file in place.
